【COMPSCI 335】 Week 11 Security Considerations

发表于2026-11-05|更新于2026-11-05|技术学习COMPSCI 335 Web Programming and Distributed Services

Security Intro

Application Security

Anything that has a potential to execute has a security concern.

  • If we are app users, execute only apps that come from a trusted party.
  • If we are app makers, can we trust our users?

A Web Application

The client that runs on a browser is the user-facing part.

Servers offer services and data to support the client.

A network supports the transfer of data and results.

Multi-tier execution (client, application servers, database servers) adds further complexity.

Web Application Security

In using a web application, we trust many parties.

  • The browser
  • The device the browser is running on (+ OS + other apps on the device)
  • The server(s) the browser is connecting to
  • The network connecting the client and the server(s)
  • The data

If any of them is compromised, we are potentially in for trouble.

Social Engineering

Phishing attacks — mostly based on social engineering.

Legal boundaries aren’t always clear.

Typosquatting (sting site, URL hijacking).

Some Common Attacks

  • Compromised devices.
  • Database attacks — SQL injection(SQLi).
  • Cross-Site scripting(XSS).
  • Cross-Site request forgery(CSRF).
  • Path traversal attacks.
  • Compromised passwords.

A Compromised Device

Trusting Devices

One should be mindful trusting devices which someone else had access to. Trusting a compromised device is likely to be harmful!

DNS Pollution

DNS resolves hostnames to IP addresses. If one compromises a DNS server, then valid domain names can be mapped to IP addresses controlled by the offender. A compromised computer can be configured to point to a malicious DNS server.

Virtual Hosting and Trojan Horses

Virtual hosting allows a single physical server to host many sites.

Running several Trojan horses on the compromised computer allows stealing multiple information.

Cross-Site Scripting(XSS)

Cross-Site Scripting

A code injection vulnerability. An attacker is able to inject potentially malicious content into a website and deliver/execute them under the privileges of the site.

This could be HTML(HTML injection) or JavaScript(code injection) that could cause greater grievance.

The slide demonstration supplies an HTML event handler such as <img src="x" alt="pix" onerror="alert('hello')"/>. If untrusted input is interpreted as HTML and event handlers are allowed, it can execute code.

A particular script failing to execute does not establish that the injection point is safe. In particular, scripts inserted through innerHTML behave differently from event-handler attributes. Treat the slides’ browser-filter discussion as historical context.

Reflected vs. Persistent XSS

The XSS attacks above are called reflected XSS. This is because the script is reflected to the user rather than being stored on a site.

Persistent XSS attacks are when the script or code is stored on the attacked server. This is a lot more damaging—any user viewing this content can be affected by the script.

E.g., posting messages on a vulnerable forum.

Mitigating XSS

For user-supplied text, create text nodes or assign textContent.

Assigning the same input to innerHTML parses it as markup. HTML escaping represents special characters such as <, >, and & as text. The required escaping or validation depends on the output context.

A server-stored value can still be untrusted input. Persistent XSS becomes possible when that value is later rendered as executable markup.

SQL Injection

SQL

SQL is used to query and modify relational databases. SQL injection occurs when user-supplied data changes the structure of a dynamically constructed SQL command.

Sample SQL Queries

Sanitize Inputs

Remove, replace, or escape characters that lead to attacks. E.g., the single quote.

Legit users suffer. Would Tim O’Reilly be happy to be called Tim OReilly or Tim O\'Reilly?

Every single user input needs to be mindfully sanitized.

Should character “equivalents” be considered? E.g., O'Reilly vs. O’Reilly.

Alternative: Treat data as data – never as code.

Parameterized Queries

Insertion Using LINQ to SQL

Data and SQL Commands

The slide example inserts a password hint into a command string. An input containing a closing quote, a second SQL statement, and a comment marker can change how that command is parsed.

In the parameterized version, the hint is supplied as a parameter value. Its punctuation remains part of the stored text. The example models SQL construction only.

The LINQ to SQL example also turns ordinary property values into SQL parameters. The protection comes from parameter binding. Concatenating input into a raw SQL command still needs separate attention.

Cookies, Sessions and Same-Origin Policy

HTTP Sessions

It won’t be good user experience if we need to authenticate every single HTTP request. Logging on to a site requires persistence – at least for a reasonable duration.

The browser transparently exchanges credentials, cookies, session IDs to make this happen.

A session is application-level state built on top of stateless HTTP. In the course example, login creates a session identifier that lets the server associate later requests with the user.

Cookie Headers

The server asks the browser to store a cookie through a response header.

The browser sends an applicable stored cookie through a request header.

Cookie scope and attributes determine when it can accompany a request. A cookie associated with secret.org does not become a cookie belonging to bad.org merely because the user visits both sites.

What Makes an Origin?

For the HTTP(S) examples in the course, an origin is the combination of scheme, hostname, and effective port.

Assume the document is served from http://www.site.org/foobar/page.html.

Resource URL Same origin? Reason
http://www.site.org/bar/data Yes Path differs, origin is unchanged
http://www.site.org:80/data Yes 80 is the default HTTP port
https://www.site.org/data No Scheme differs
http://www.site.org:81/data No Port differs
http://site.org/data No Hostname differs
http://m.www.site.org/data No Hostname differs

The relevant origin is the document’s origin. Loading an external script into that document does not give that script a separate page origin for its requests.

Same-Origin Policy

The browser’s same-origin policy restricts access to data belonging to another origin. This protects a logged-in user’s information from scripts in an unrelated page.

Cross-origin embedding of resources such as images and classic scripts is often allowed. That does not grant a page general access to the embedded resource’s contents. A cross-origin iframe also retains origin boundaries around its document.

For fetch, the browser applies CORS checks before exposing a cross-origin response to the calling script. Some requests can reach the server even when the script cannot read the response. This distinction matters for CSRF.

Cross-Origin Resource Sharing

Allowing Cross-Origin Reads

CORS lets a server opt into cross-origin access using response headers. The browser checks the permission before exposing the response.

A public resource can allow origins with

Adding this header to the client’s request does not grant permission. It is the resource server’s response that must supply the appropriate CORS headers.

Credentials

A cross-origin fetch that needs cookies explicitly requests credential inclusion.

For a page at https://good.org, the responding server must permit that origin and credentialed access.

Cookie eligibility still depends on cookie attributes and browser policy. These headers grant permission to read a credentialed response. They do not by themselves force the browser to send cookies.

A credentialed CORS response needs a specific allowed origin. The wildcard * does not satisfy that check.

Preflight

Some cross-origin requests require the browser to send an OPTIONS preflight before the actual request, for example a request using an Authorization header.

The preflight describes the proposed method and headers.

The server grants permission through response headers such as

Keep the request’s Access-Control-Request-* headers distinct from the response’s Access-Control-Allow-* headers. A successful preflight permits the actual request to proceed.

Diagnosing a CORS Error

The course example includes a misspelled URL, corss/Version. A wrong endpoint may produce a response without the expected CORS headers. Check the URL, HTTP method, request headers, and server response.

Using mode: "no-cors" can produce an opaque response. JavaScript cannot inspect its body or ordinary status information, so this does not provide readable cross-origin data.

CORS Proxy

A proxy performs a server-to-server request, then returns the result with suitable CORS headers. Browser CORS restrictions apply to the browser’s response access.

The course proxy example supplies the destination as an encoded query parameter.

The browser communicates with the proxy origin. It does not automatically give the proxy the user’s cookies for the destination origin. A proxy can retrieve public data without acquiring the user’s destination session.

JSONP

JSONP returns JavaScript that calls a supplied callback with the data.

A classic script element can load that response from another origin.

Define the callback before the downloaded script executes. Here defer also ensures that the span exists when the callback runs.

For the click-to-load exercise, the click handler creates a script element. After the response loads and executes, it calls the callback. The callback can update the page and remove the temporary script element.

JSONP gives the external response the ability to execute code in the page. The course presents this as a legacy technique with security concerns.

Cross-Site Request Forgery (CSRF)

Forging a User’s Action

CSRF exploits a browser’s automatic inclusion of applicable credentials. A user logged into a bank can be tricked into making a request that the bank accepts as an intended action.

The slide example uses a link shaped like http://www.bank.com/send?m=1000&to=lucifer. If following that link sends an applicable session cookie and the server treats the GET request as a transfer instruction, the action can occur without the user’s intended authorization.

The attacker may only need to cause the action. Reading the response is not required.

Mitigation

The slides discuss strong session identifiers and checking Origin or Referer. Strong identifiers reduce session guessing, while source checks help distinguish requests from an unexpected origin.

Strong identifiers alone do not stop a browser from sending a valid session cookie on a forged request. Anti-CSRF tokens bind state-changing requests to the intended session or workflow. Appropriate cookie SameSite settings provide another restriction on cross-site credential use.

A server should validate the relevant protections. A client-side check can be bypassed by submitting requests directly.

The Origin header identifies the scheme, hostname, and port. It does not distinguish applications at different paths on the same origin. The slides explicitly note this limit.

XSS vs. CSRF

Attack What is exploited Typical consequence
XSS Untrusted content interpreted as executable markup or script Code executes with the page’s privileges
SQLi Untrusted input incorporated into SQL command structure Database commands are changed
CSRF An unintended request carries applicable user credentials Server performs an unintended action

The slides describe XSS as making the client trust attacker-controlled content from a site, and CSRF as making the server trust an unintended client request.

Reading Security Questions

Trace the input from its source to the operation that interprets it. For HTML, distinguish text insertion from markup parsing. For SQL, distinguish command text from parameter values. For a request, check origin, credentials, server authorization, and whether the attacker needs to read the response.

The 2025 paper separates same-origin comparisons (Questions 45–46) from vulnerability recognition (Questions 47–50). For X/Y/Z questions, evaluate each statement before selecting the matching option.
