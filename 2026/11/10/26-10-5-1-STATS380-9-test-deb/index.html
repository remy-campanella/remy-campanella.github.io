Building Tests from Small Examples

Use inputs whose expected results can be checked by hand. For a table-boundary function, cover a valid start, a row inside a table, a note row, the final row, a missing label and invalid arguments. Changing one condition at a time makes failures easier to locate. The tableStart() example uses the lecture’s first-column rule and handles the final row explicitly.

Test-driven development starts with a test that exposes a defect. Confirm that it fails, then change the implementation until it passes and rerun the existing tests. For regression testing, save a trusted result before a change, then rerun the same input and compare. Use source() to run the checks in a test script together.

  • identical(actual, expected) checks that type, structure and values match exactly.
  • all.equal(actual, expected) returns TRUE when the comparison succeeds and a description when it finds differences. Use isTRUE() around it in a condition.
  • tools::assertError(expr) checks that the expression raises an error. If the contract specifies an error class or message, verify that too.

Tracing Warnings and Errors

The lecture workflow fails on the 2021 Young People worksheet. The plotting code calls seq() to position labels and reports a non-finite endpoint, alongside a warning that coercion introduced NA values. Reducing the batch to a single table traces the issue to a measure column containing "_" as a missing-value marker. This caused the numeric data to be read as character values.

  1. Read the full error and warning messages and note which call and inputs triggered them.
  2. Use traceback() immediately after the failure to see whether the call stack leads to batch import, table processing or plotting.
  3. Reduce the input to the table that reproduces the problem. Use str(), class() and head() to inspect intermediate values, including range endpoints and group labels.
  4. Find the first step that violates an assumption. After fixing the import, keep a small example containing the missing-value marker as a regression test.

Debugging Tools

Tool Use
traceback() Shows the call stack for the most recent uncaught error.
debugonce(f) and debug(f) Enter the debugger on the next call or on every call to f, respectively. Clear persistent debugging with undebug(f).
browser() Pauses at the inserted statement so you can inspect the local environment.
options(error = recover) Lets you choose a call frame after an interactive error. Restore the previous setting when finished.

At the debugger prompt, use n to step, s to step into a call, c to continue and Q to quit debugging. If a variable has the same name as a command, use a call such as print(n) to inspect it.
